# Senju 千手

**全双工 Agent 运行时：一颗心，千只手。**

大多数 agent 是“半双工”的：干活的时候听不进你说话。Senju 让一个对话式助手边干活边听你说，同时做好几件事，你永远不用排在一个忙碌的工具调用后面。名字来自千手观音（日语读作 Senju）：一颗心，千只手。

[English](README.md) · [设计文档](docs/DESIGN.md)

大多数 agent 一次只处理一轮。它花两分钟导出报表时，你问一句简单的话也要等两分钟；你说"停"，也得等当前工具调用返回。senju 对用户始终是同一个声音，但每件事都由一只独立的**手**（hand）来做。每只手有自己的工具循环和自己的对话记录。新消息先经过**分派**，结果是下面四种之一：
- 交给正在做这件事的手（join）；
- 开一只新手（new）；
- 直接回答（reply）；
- 停掉某只手（stop）。

- **每条消息恰好安排一次。** 模型给出安排，运行时负责校验和修补。漏掉的、重复的、指错的安排都会被纠正，不会丢消息，也不会答两遍。
- **没有人排在忙碌的手后面。** 补充说明在那只手的下一步读到；无关的问题自己开一只手；"进展怎样"由分派直接根据看板回答。
- **停止是立即的。** 工具拿到 `AbortSignal`，锁当场释放。
- **共享资源安全。** 工具声明要用的资源（如 `pc.input`），按先来先得排队，不会死锁；等了多久会告诉模型。
- **对缓存友好。** 每只手的记录只追加不改写，人格前缀共用，支持前缀缓存的服务商可以命中缓存。
- **零依赖。** Node ≥ 20。模型通过一个很薄的适配层接入，自带 OpenAI 兼容适配器（OpenAI、DeepSeek、vLLM、Ollama、OpenRouter 等）。

快速上手、API 和测试见 [README.md](README.md)。离线演示：`node examples/offline-demo.js`。

## 基准

`node bench/run.js` 用同样的模拟模型（每次调用 600 ms，分派 400 ms）和同样的工具，对比 senju 与经典单循环 agent（一次一轮，新消息在工具轮之间吸收）。测的是架构本身，不是模型好坏。

| 场景 | 单循环 | senju |
|---|---:|---:|
| 8 秒任务进行中问一句简单的话：首次回复 | 7.7 s | 1.2 s |
| 10 秒任务进行中说"停"：生效时间 | 9.2 s | 0.6 s |
| 两件独立的事：全部完成 | 15.8 s | 9.4 s |
| 任务、补充、第二个任务、"谢谢"：全部完成 | 11.8 s | 7.4 s |
| 上一行的模型调用次数 | 3 | 8 |

代价是模型调用更多：有任务在进行时，每批新消息要多一次分派调用，每只手也有自己的调用。有前缀缓存时，这些调用的大部分 token 都能命中缓存。

### 真实模型

同样的设计跑在一个日常使用的个人助手里。我们在它上面把原来的单循环和 senju 式分派同时各跑一份做对比：6 道多消息题 × 3 轮，先让它用真模型查网页，几秒后再发第二条消息。

| 指标（21 条追加消息） | 单循环 | senju |
|---|---:|---:|
| 首次回应 中位数 | 11.8 s | 5.1 s |
| 首次回应 p90 | 21.7 s | 10.4 s |
| 说"算了不用了"之后停下 | 22–28 s | 3.5 s |
| 通过 | 18/18 | 18/18 |

每条追加消息的分派约 3 秒、约 500 token。短任务里的补充没有变快：这一轮本来几秒就结束，单循环也能很快接上。助手忙得越久，收益越大。
